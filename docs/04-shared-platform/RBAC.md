# Role-Based Access Control

Evidence: "Serious Security" tile (EV-041); committee vs owner visibility (EV-032, EV-038); contractor apps (EV-082). Internal model UNKNOWN → **PROPOSED** below.

## Model
- `Permission` = `<module>.<resource>.<action>` (static catalog in code).
- `Role` = named set of permissions (system roles below; tenant custom roles = backlog BL-08).
- `RoleAssignment{user_id, tenant_id, role, scope_type: tenant|scheme|property|region|lot|supplier|client, scope_id?}`.
- **Decision** `can(user, permission, resource)`: ∃ assignment in `resource.tenant_id` whose role grants permission AND scope contains resource (tenant ⊇ region ⊇ property; tenant ⊇ scheme ⊇ lot; supplier = resource.supplier_id; client = resource.client_id).
- Enforced in: API middleware (route permission) → service layer (resource scope) → Postgres RLS (tenant). AI tools call the same service layer (BR-AI-01).
- Row filtering for lists uses scope predicates generated by the policy module (`scopeFilter(user, 'fm.workorder.read')`).

platform_admin, tenant_admin, strata_manager, strata_accountant, committee_member, owner, occupier, fm_manager, fm_coordinator, technician, contractor, fm_client, auditor.
